# 量化组合模块：绩效归因与实盘展示

> 借鉴 [waditu/czsc](https://github.com/waditu/czsc) 的 `scripts/auto-czsc-quant/` 与 `wbt` 权重回测口径。
> **可照搬的 alpha 很少，值得学的是架构和评价体系。**

---

## 一、先说清楚：这套和原有回测有什么不同

本站原来有两套回测，现在加了第三套。三者**口径不同、互不替代**：

| 模块 | 视角 | 回答什么问题 | 核心输出 |
|---|---|---|---|
| 结构分析 · 信号历史表现 | 信号点 | 信号后 N 天涨没涨 | 命中率 |
| **因子回测**（btengine） | **交易层** | 按规则交易，资金曲线长什么样 | 逐笔明细、资金曲线、利用率 |
| **量化组合**（本模块） | **组合层** | 多品种组合整体表现如何 | **27 项绩效归因** |

**为什么需要第三套**：前两套都是"单标的视角"。实盘是多品种并行的，
组合层的夏普、卡玛、多元/空占比、品种数量这些指标，单标的回测根本算不出来。

## 二、从 czsc 学到的三件事

### 1. 指标口径（27 项，直接对齐 wbt）

czsc 的 `auto-czsc-quant` 用 `WeightBacktest` 算组合绩效。27 项指标不是随便列的，
它构成一个**完整的评价闭环**：

| 维度 | 指标 | 为什么要有 |
|---|---|---|
| 收益 | 绝对收益、年化收益 | 基础 |
| 风险调整 | 夏普、卡玛 | 收益要除以风险才有可比性 |
| 回撤 | 最大回撤、新高占比、**新高间隔** | 新高间隔衡量"多久能回本"，比回撤深度更贴近体感 |
| 波动 | 年化波动率、**下行波动率** | 下行波动只算亏损波动，更符合风险直觉 |
| 交易 | 交易次数、年化交易次数、单笔盈亏比、单笔收益、交易胜率 | 摩擦成本与每笔质量 |
| 周期胜率 | 日/周/月/季/年胜率 | **多周期胜率是 wbt 的特色**，能看出策略在长周期是否站得住 |
| 持仓 | 持仓K线数、多头占比、空头占比 | 资金利用与方向偏好 |
| 范围 | 品种数量、开始/结束日期 | 结论的适用边界 |

**几个容易搞错的点（我们按 wbt 口径对齐）**：

- **年化用 252 交易日**折算，不是 365 日历天
- **卡玛 = 年化收益 ÷ |最大回撤|**
- **单笔收益单位是 BP**（万分之一），不是 %
- **新高间隔** = 两次净值新高之间的最大交易日数
- **多头占比** 按持仓权重为正的 K 线数占比

### 2. 权重聚合方式

czsc 的做法：单标的回测 → 提取 `holds` → 聚合成 `weights` → 组合回测。

我们照搬这个思路，但明确了一个关键口径：

```
组合收益 = Σ(品种日收益 × 品种当日权重) ÷ Σ|权重|
```

**分母用 Σ|权重| 而不是品种数** —— 否则"今天只有 3 个品种有信号"会自动放大 3 倍仓位。
这是权重回测最容易被忽略的坑。

### 3. LLM 优化闭环（我们没照搬，但想说清楚为什么）

czsc 的 `auto-czsc-quant` 有一个很漂亮的闭环：

```
LLM 生成候选 Position
  → 校验（锁定不可变字段 interval/timeout/stop_loss/T0）
  → 回测（多品种）
  → 评分 sharpe*0.35 + annual*0.30 - maxDD*0.25 - turnover*0.10 + coverage*0.10
  → 硬惩罚（交易<3次 或 覆盖率<50% 直接扣分）
  → 写 journal（SQLite 记录每一轮）
  → 反馈给下一轮 LLM
```

**设计亮点**（值得记住的设计模式）：

| 设计 | 为什么重要 |
|---|---|
| `lock_immutable_fields` | 强制覆盖 LLM 提交的止损/超时参数，防止它"改参数作弊" |
| 硬惩罚项 | 样本太少/覆盖太低的候选直接扣分，防止过拟合小样本 |
| journal 落库 | 每轮结果可追溯，避免重复试同一个假设 |
| 评分权重固定 | 不让 LLM 参与评分，否则等于自己给自己打分 |

**我们没照搬的原因**：本项目没有 LLM 生成策略的能力，也没有历史 journal 数据。
强行接一套"假闭环"不如先把评价体系做扎实。**但评分公式和硬惩罚的设计可以直接用**，
将来若要做参数搜索，这套打分逻辑现成可用。

## 三、实现

### 文件

```
server/lib/quantmetrics.js   27 项指标计算（对齐 wbt 口径）
server/lib/portfolio.js      组合回测（信号→权重→组合日收益→指标）
web/js/pages/quant.js        页面（8 组分区展示 + 净值曲线 + 分品种）
```

### API

```
GET /api/quant/portfolio?markets=CNF&maxSymbols=10&period=day
```

参数：
- `markets`：A / US / CR / CNF / HK，逗号分隔
- `symbols`：自定义标的 `A:600519,CNF:RB0`（优先于 markets）
- `maxSymbols`：品种数上限（默认 12，最多 40）
- `maxWeightPerSymbol`：单品种最大权重（默认 1）
- `feeBps` / `slipBps`：成本

### 信号 → 权重的转换

```
买点信号 → 目标权重 = maxWeightPerSymbol
卖点信号 → 目标权重 = 0
未触发   → 保持上一个状态
信号次日生效（无未来函数，与 btengine 同一套确认延迟机制）
```

## 四、页面设计：为什么这样展示

**核心问题：27 个数字平铺出来没人看得懂。**

所以按语义分成 8 组，每组回答一个具体问题：

| 分组 | 回答 |
|---|---|
| 收益 | 赚了多少 |
| 风险调整 | 性价比 |
| 回撤与新高 | 抗压能力 |
| 波动 | 净值抖动 |
| 交易行为 | 怎么做的 |
| 单笔与胜率 | 每笔质量 |
| 周期胜率 | 各周期为正的比例 |
| 回撤范围 | 结论的边界 |

**配色规则**：`最大回撤 / 年化波动率 / 下行波动率 / 新高间隔` 是越小越好（标红），
其余越大越好（标绿）。这个 `inverted` 列表直接对齐 wbt 的 `_INVERTED_STATS`。

**顶部判定卡片**直接把三个关键判断翻成人话：

> 组合表现：负收益 · 夏普 -0.03
> - 夏普 ≤ 1，承担的风险没有得到足够补偿
> - 卡玛偏低，回撤相对收益过大
> - 年化交易 9 次，换手低、摩擦小
> - 持仓方向：多头 100% / 空头 0%（纯多头策略）

**口径说明栏**：把 6 个最容易搞错的口径写在页面上，避免误读。

## 四点五、配色语义（一个踩过的坑）

A 股配色里 `--up` 是**红**、`--down` 是**绿**。用它表达"指标好坏"会严重误导：

```
最大回撤 39.44%  → 是正数 → 套用 --up → 显示红色，看起来像"好"
最大回撤 12%     → 也正数 → 同样红色
```

**回撤大小和数字正负无关。** 所以量化模块另立一套语义色：

| 类 | 含义 | 用于 |
|---|---|---|
| `q-good` | 绿 | 收益/夏普/卡玛为正；回撤/波动/新高间隔低于阈值 |
| `q-bad` | 红 | 反之 |
| `q-neutral` | 常规色 | 计数类（交易次数、品种数量）或中等区间 |

**越小越好的指标按分档着色**（不是按正负）：

| 指标 | 绿（≤） | 中 | 红（≥） |
|---|---|---|---|
| 最大回撤 | 15% | 15~30% | 30% |
| 年化波动率 | 15% | 15~30% | 30% |
| 下行波动率 | 10% | 10~20% | 20% |
| 新高间隔 | 60 日 | 60~120 日 | 120 日 |

有测试锁住这条：`最大回撤 39.44 → q-bad`（若按正负判断会错判成 q-good）。

**页面内只用一套配色**：分品种表的收益也用 `q-good/q-bad`，不再混用涨跌色。

## 四点六、结果区三层结构（v3.9.1）

27 个数字摆出来，专业人士能读，小白读不了。所以结果区改成三层，**每层回答一个不同的问题**：

| 层 | 回答 | 组件 |
|---|---|---|
| ① **评分仪表盘** | 这套**能不能用** | 0-100 总分 + 四维度条 + 一句大白话结论 |
| ② **四个大数字卡** | **具体多少** | 年化/夏普/回撤/胜率 + 迷你走势 |
| ③ **品种贡献排行** | **问题出在哪** | 横向排行条，绿色贡献、红色拖累 |

27 项完整指标保留在下方，供想深究的人查。

### 评分是怎么算的（可查、可质疑）

每个维度先做**区间对照**得 0~满分，再加权求和——不是隐式加权，每个区间都写死在 `server/lib/score.js`：

| 维度 | 打分规则 |
|---|---|
| 收益能力 | 年化收益 -20%～+30% 线性映射 |
| 风险调整 | 夏普 -0.5～2.0 占 70%，卡玛 -0.5～2.0 占 30% |
| 回撤控制 | 最大回撤 60%～5% 反向线性 |
| 交易质量 | 胜率 20%～65% 占 45%，盈亏比 0.5～2.5 占 35%，年化换手 5～40 次占 20% |

**评级门槛不随权重变化**（否则会出现"换个权重就变优秀"的荒谬结论）：

```
80+ 优秀 · 60-79 可用 · 40-59 边缘 · 20-39 偏弱 · <20 不合格
```

### 权重可切换

评价标准本就因人而异，写死一套等于把偏好强加给用户。三种预设：

| 预设 | 收益 | 风险调整 | 回撤控制 | 交易质量 | 适用 |
|---|---|---|---|---|---|
| 均衡（默认） | 30 | 30 | 25 | 15 | 通用 |
| 保守 | 20 | 25 | 40 | 15 | 怕亏、看重回撤 |
| 激进 | 45 | 25 | 15 | 15 | 只看能不能赚钱 |

### 结论从数据生成，不是套模板

```
这套组合处于边缘水平；主要短板在风险调整——夏普 0.43，承担的风险没有得到足够补偿。
```

短板文案按**最弱维度**动态选择，不是固定句式。

⚠️ 一个踩过的 bug：`weakest.pct` 起初没有计算（dim 对象只有 `got`/`max`），
导致 `undefined < 40` 恒为 false，**短板说明整段丢失**。
已修并加回归测试锁住。

## 四点七、评分组件已复用到因子回测页（v3.9.2）

结果区三层结构现在**两页共用同一套组件** `web/js/pages/scorewidget.js`：

| 页面 | 评分输入来源 | 说明 |
|---|---|---|
| 量化组合 | 27 项组合指标 | 原口径 |
| 因子回测·单标的 | `annualReturnPct / sharpe / maxDrawdownPct / winRate / payoff` | 直接映射 |
| 因子回测·批量 | `medianAnnualPct / medianSharpe / medianDrawdownPct` + 汇总胜率 | 取中位，避免极值 |

两套回测字段名不同，用 `SCORE.fromBacktest(stats, isBatch)` 做归一化，
避免在两个页面各写一份打分逻辑。

### ⚠️ 又踩了一个「字段不存在」的坑

批量汇总里我写了 `r.annualReturnPct`，但 `batch.js` 的 rows **没有这个字段**
（只有 `totalReturnPct` 和 `years`），导致 `medianAnnualPct` 恒为 **null**，
评分里「年化收益」这一维度永远得 0 分。

修正：从 `totalReturnPct` 与 `years` 现算年化
`(1 + total/100)^(1/years) - 1`。修完后中位年化从 `null` 变成 `0.33%`，
总分从 44 → 46。

**这是本项目第二次因为"引用了不存在的字段"出 bug**
（上一次是 `weakest.pct`）。已加回归测试：
断言 `medianAnnualPct` 不能是 null。

## 四点八、权重切换 / 并排对比 / 历史存档（v3.10）

### ① 权重切换已上手机

量化组合与因子回测两个手机弹层都加了「均衡 / 保守 / 激进」切换，
点了直接重新请求（评分在服务端算），不需要重新选标的。

### ② 并排对比

点「与上次参数对比」→ 选一个改动项 → 点「开始对比」，一次跑两组：

```
        A · 原始               B · 新参数
   ┌──────────────┐    -3 分   ┌──────────────┐
   │      54      │   A 更好   │      51      │
   │     边缘     │            │     边缘     │
   └──────────────┘            └──────────────┘

   收益能力   15.8  →  15.3   -0.5
   风险调整   10.7  →   9.9   -0.8
   回撤控制   17.1  →  16.5   -0.6
   交易质量   10.3  →     9   -1.3
```

**做了什么**：`GET /api/bt/compare?a=<base64url>&b=<base64url>`，
两组参数并行跑（`Promise.all`），返回两份结果 + 差异表（分数差、四维度差、关键指标差）。

**一个设计取舍**：没有做成"自动对比上次"，而是让用户**选一个改动项**。
因为实际想回答的问题通常是"如果我加止损会怎样"，而不是"上次跑的是什么"。

⚠️ **可调项必须按回测类型裁剪**：
量化组合是"信号→权重聚合"，**没有止损止盈概念**。
第一版把 `stopPct` 放进了对比面板，结果两组分数完全一样（差 0 分）——
因为后端根本不认这个参数。现在量化对比只提供：
换笔标准 / 单品种仓位上限 / 手续费 / 品种数。

### ③ 历史存档

每跑一次回测**自动记一条**（可加 `?nosave=1` 关闭）。

**按指纹分组**，而不是平铺：
- 指纹 = 回测类型 + 标的 + 关键参数 的 sha1 前 12 位
- **打分权重不参与指纹**——同一份回测换权重应该还能对比
- 每组最多 30 条，总量上限 200 组，超出淘汰最旧

为什么必须分组：10 套参数 × 20 次执行 = 200 条，平铺混在一起看不出任何趋势。
分组后每组有自己的时间序列，才能算"较上次 +6 分"。

存储：`data/backtest-history.json`，原子写（先写 .tmp 再 rename），
同一秒内重复执行会覆盖而不是追加（避免刷新页面刷出一堆）。

API：
```
GET  /api/bt/history?all=1        列出所有存档（按最近更新排序）
GET  /api/bt/history?key=<key>    单条详情
POST /api/bt/history/clear        清空（带 ?key= 则删单条）
```

### ⚠️ 两个必须修的坑

**坑 1：指纹对"字段是否存在"敏感，导致趋势图永远是单点**

同一组参数，一次带 `entry:'both'` 显式传参、一次不带（走默认值），
`fingerprint()` 算出的哈希完全不同 → 每次跑都**新建一组** → 每组只有 1 个点。

实测：手工造的数据与真实调用被拆成两组，各 1 条。

修正：指纹计算前先跑 `normalize()`，把**所有字段填上默认值**
（`entry` 默认 `both`、`stopPct` 默认 `0`、`biStyle` 默认 `new`…），
数值统一转 Number。修完后两种写法得到同一指纹。

> 有测试锁住：`带默认值 vs 不带默认值必须同指纹`，
> 同时 `改止损 / 改笔标准必须区分`（防止归一化过头把所有配置合一起）。

**坑 2：纵轴固定 0-100 会把 8 分变化压成横线**

第一版用固定 0-100 纵轴（想着"分数本来就 0-100，保持一致"），
结果 40→48 的变化在图上是**一条几乎水平的线**，完全没有趋势感。

改成：**至少 30 分的窗口**，以数据范围为中心，再夹在 0-100 内。
- 8 分变化 → 窗口 30 分，曲线有明显坡度
- 80 分跨度 → 保持原范围，不被强撑
- 评级参考线（60/40）只在落在窗口内时才画

> 有测试锁住这三个边界。

## 五、如何用于实盘

### 1. 组合体检

跑一次多品种组合，看三个数就够：
- **夏普 > 1** → 风险调整后可以
- **卡玛 > 0.5** → 回撤相对收益可接受
- **年化交易次数 < 30** → 摩擦成本可控

### 2. 品种筛选

页面底部「分品种表现」按合计收益排序，**能直接看出哪些品种适合这套逻辑**。
实测期货 8 品种里 CU0 合计 +19.18%、SF0 −18.75%，差异极大。

### 3. 多空结构

`多头占比 / 空头占比` 反映了策略的方向偏好。当前实现是**纯多头**
（空头 0%），说明缠论买点驱动天然偏多 —— 这也是为什么在下跌市表现更好（少亏）。

### 4. 周期胜率诊断

**日胜率 37.55% 但季胜率 50%、年胜率 50%** —— 说明这套逻辑在短周期不占优（频繁小亏），
但在长周期能站住。实盘含义：**别盯日线盈亏，看季度表现**。

## 六、诚实的边界

| 事项 | 说明 |
|---|---|
| 空头占比恒为 0 | 当前只做多（买点驱动）。做空需在信号层扩展，未实现 |
| 组合收益分母 | 用 Σ\|权重\|，与"固定品种数"口径不同，注意可比性 |
| 年化 252 | 加密 7×24 交易，用 252 会低估年化 |
| 未做 walk-forward | 组合层目前是单次回测，过拟合风险高于因子回测（后者有滚动验证） |
| 无 LLM 闭环 | 见第二节，没接是因为没有策略生成能力，不是遗忘 |

## 七、指数相关提醒
