# 缠论：从理论到实践的完整链路

> 这份文档回答一个问题：**为什么同一张图，不同人、不同软件画出来不一样？我们怎么把这件事做准、做可复核？**

---

## 一、先说清楚一堆绕不过去的坎

我读了社群里大量关于缠论的讨论，反复出现的困难集中在四件事：

### 1. 笔的划分：缠师自己改过定义

| | 老笔（108 课早期） | 新笔（2007-09-18 博文） |
|---|---|---|
| 出处 | 《教你炒股票》前期课程 | 《忽闻台风可休市，聊赋七律说〈风灾〉》 |
| 条件一 | 顶底分型经包含处理后不共用 K 线 | **相同**（这条绝对不能放松） |
| 条件二 | 顶底之间**至少 1 根独立 K 线** | 最高 K 与最低 K 之间（不含端点）**至少 3 根 K 线**，不考虑包含 |
| 结果 | 严格，笔少 | 宽松，能救回大量"顶底间只隔 1~2 根"的笔 |

**实测（600519 日线，601 根）**：

| 标准 | 笔数 | 中枢数 | 走势完美度 |
|---|---|---|---|
| 新笔 | 55 | 11 | 已完成 |
| 老笔 | 47 | 10 | 未完成 |

**同一份数据，仅仅换个笔标准，中枢数量、走势是否完成的结论全都变了。**

这就是[缠友讨论](https://m.book118.com/html/2017/0212/90661710.shtm)里说的"缠论不能像波浪理论一样最后整成千人千缠"。本项目的做法是：**把标准显式化，让你随时切**，而不是偷偷替你选一个。

### 2. 数据差异导致划分不同

缠师本人[在博文里说过](http://www.360doc.cn/article/78654722_1085581551.html)：

> "本ID平时交易时不用同花顺……两套系统的数据经常有点小出入，有时候偷懒，就照抄过去，偶尔就会出问题。"

**不同数据源的分时/日线收盘价哪怕差一分钱，分型就可能变，笔就跟着变。** 所以本项目：
- 所有源都有降级链，并标注实际用的哪个源
- `audit` 里给出 `styleDivergence`（两种笔标准的差异百分比），≥10% 会主动提示

### 3. 中枢扩展 vs 扩张：连老手都常常搞混

这是吵得最凶的一个概念。区别在于**用哪个区间判定重叠**：

| | 中枢扩展 (extension) | 中枢扩张 (expansion) |
|---|---|---|
| 用哪个区间 | **中枢区间 ZD~ZG** | **波动区间 DD~GG** |
| 情形 | 离开后出现三类买卖点，**又回到原中枢内** | 两个同级别同向中枢的**波动区间**重叠 |
| 含义 | 三类买卖点失败，原中枢继续有效 | 按"走势级别延续定理二"，更高级别中枢产生 |

**最容易搞错的地方**：扩张判定用的是 `dd~gg`（波动区间），**不是** `zd~zg`（中枢区间）。用错了会把趋势误判成扩张，或者反过来。

本项目对每一对相邻中枢都会区分：
- 波动和中枢区间都重叠 → 「区间重叠型扩张」
- **只有波动重叠、中枢区间不重叠** → 「波动重叠型扩张」（最易误判，会重点标出来）

### 4. 区间套在实盘很少"完美"出现

有位[实盘者的总结](https://blog.eastmoney.com/m9528094005815840/blog_220430587.html)非常到位：

> "标准的区间套很少的，背驰段里又有背驰段。那是理想状态。更多的是如果你在日线上已有背驰，但在次级别中不知道在哪一个级别里才能找到背驰段的背驰段……很多人在多级别的方程中迷失了自己。"

所以本项目的区间套：
- **不硬凑**——没形成就明确说"未形成多级别共振"
- **窗口按背驰段收紧**，而不是整段中枢（详见第四节）
- 固定"操作级别 + 最多一个次级别"的建议，避免越看越晕

## 二、九步链路：每一步回答一个问题

这是本项目的骨架。`/api/system` 一次返回全部九步，每步都带**证据**和**置信度**。

| 步 | 问题 | 输出 | 置信度依据 |
|---|---|---|---|
| ① | 数据够用吗？新鲜吗？ | 根数、是否陈旧、数据源 | 陈旧→low；<200 根→medium |
| ② | 笔怎么画的？换标准会变吗？ | 标准名、新/老笔数、差异率、密度 | 差异 ≥15%→low，≥8%→medium |
| ③ | 现在什么结构？ | 笔/线段/中枢数、趋势类型、位置 | 无中枢→low |
| ④ | 中枢在演化吗？ | 扩展/扩张/9段升级 | 出现"仅波动重叠"→重点提示 |
| ⑤ | 走势走完了吗？ | 已完成 / 延伸中 / 离开中 | 未完成→只跟踪不下结论 |
| ⑥ | 按哪个级别操作？ | 同级别分解段数 + 唯一性 | 有相邻同向→low |
| ⑦ | 有买卖点吗？ | 最近信号 + 背驰 | 无信号→不动 |
| ⑧ | 大小级别共振吗？ | 区间套递归结论 | 未共振→仓位降低 |
| ⑨ | 别人能复现吗？ | 笔标准 + 中枢数 + 数据区间 | 确定性规则，必可复现 |

**第 ⑨ 步是关键。** 缠论最难的不是"说不出结论"，是"说完别人复现不了"。本实现全部是确定性规则：同样数据 + 同样参数 = 同样结果（有测试锁住）。

## 三、实践中的注意事项（自动检测）

系统会自动扫描这些坑，命中就在面板上标出来：

| 坑 | 触发条件 | 为什么要提醒 |
|---|---|---|
| 划分标准差异大 | 新旧笔差异 ≥10% | 跨软件对照前先统一标准，否则鸡同鸭讲 |
| 笔密度过高 | >14 笔/100 根 | 标准过松或级别太小，假信号多 |
| 笔密度过低 | <4 笔/100 根 | 单边行情或标准过严，中枢很少 |
| 尚无中枢 | 中枢数 = 0 | 此时谈买卖点没有依据 |
| 扩张形态 | 存在"仅波动重叠" | 最易误判成趋势延续，级别可能已升级 |
| 走势未完成 | 完美度 ≠ complete | 可跟踪，不要当已完成走势下结论 |
| 未共振 | 区间套未成立 | 单级别信号可靠性下降 |
| 数据陈旧 | 最后一根 >45 天（日线） | 结论可能已过期 |

## 四、让画图更精准：四个具体措施

### 1. 笔标准可切换，并把差异量化

结构页右上角有「新笔 / 老笔」切换，切换后**全部结构重算**。同时 `audit.styleDivergence` 告诉你"换标准会差多少"。

### 2. 中枢区间口径修正

之前 `gg/dd`（波动区间）用整段笔的高低 `h/l` 计算，导致一根从 1142 拉到 1807 的笔把波动区间撑到 1800+，于是**几乎所有相邻中枢的波动区间都重叠**，扩张判定全命中、同级别分解退化成一整段。

现在改为用**笔的端点 `p1`** 计算——这才是"中枢震荡的最高/最低点"的本义。

### 3. 背驰段精确定位（而不是整个中枢）

缠论强调"背驰段的起点"。实现上：

1. 背驰记录里带上**比较对**：前段、本段各自的起止时间 + MACD 面积
2. 下钻窗口 = **本段起点 → 背驰确认点**（前段只是参照物，不参与收窗）
3. 与中枢范围取交集，避免跑到中枢外面

效果（600519）：周线下钻窗口从「中枢 2024-09~2025-11」精确到「背驰段 2025-06-20~2026-06-22」，60 分钟数据覆盖率从 **0% 变成 100%**，递归才真正走通。

### 4. 图上可直接高亮背驰段

区间套每层有「图上定位」按钮，点击后自动切到该级别，把**前段（灰蓝）/ 本段（金色）**两段底色 + 「背驰确认」标记画到图上，区间外压暗，底部给出面积对比。

## 五、怎么用（推荐工作流）

```
1. 先看第 ②步：差异率大不大？
     大 → 先统一标准再往下看，否则后面全是浮沙

2. 看第 ③④⑤步：结构清楚吗？走势完成了吗？
     未完成 → 只跟踪，不动手

3. 看第 ⑥步：确定操作级别
     分解不唯一 → 先合并相邻同向段

4. 看第 ⑦⑧步：有没有买卖点？多级别共振吗？
     只有单级别 → 降低仓位或等待

5. 点「图上定位」核对背驰段
     亲眼确认面积确实在缩小，而不是只看一个数字

6. 第 ⑨步抄下参数（笔标准 + 数据区间），方便事后复盘
```

## 六、诚实的边界

| 事项 | 现状 |
|---|---|
| 线段划分 | 用的是"三笔重叠 + 端点取极值"的近似，**不是**完整的特征序列缺口两种情况。已在代码注释里标明 |
| 中枢扩张后的大中枢区间 | **不自动合成**。业界对此没有唯一画法（取相邻 dd/gg 还是取上下沿，两种都有人用）。缠师 2007-04-09 回复"扩展后的划分和一般中枢正常的划分没什么区别"，即应到更高级别按原始定义重划 |
| 级别递归 | 由多级别区间套承担；单一周期内不做无限级别嵌套 |
| 小转大 / 中阴阶段 | 有概念说明，但**没有做自动识别**——这两者高度依赖主观判断，强行量化反而误导 |
| 数据覆盖 | 分钟级 600 根只能覆盖几天到几个月，递归到小级别时常"覆盖不足"，系统会明确说明而不是硬算 |

## 附：结构式必须与中枢个数一致（v3.11 修正）

### 问题

用户反馈：图上只有 1 个中枢，系统却显示结构是 `a+A+b+B+c`，应该是 `a+A+b`。

### 三处根因（都不是"写错一个字"）

**① 前端把中枢个数删掉了**

后端本来返回 `a + A + b + B + c …（16 个中枢的走势连接）`，
前端为了版面清爽用了 `res.structure.replace(/（.*?）/, '')`，
于是界面只剩 `a + A + b + B + c …`——**关键限定被删，用户自然误读**。

**② 中枢数量只放在括号里**

即使不删括号，把"16 个中枢"这种核心信息塞进括号也不对：
结构式的含义完全取决于中枢个数（1 个 = 盘整，2 个以上 = 趋势）。
现在写进主文案：`a + A + b + B + c + …　趋势延伸 · 16 个中枢`。

**③ 教学标注是无条件固定话术**

`highlight.js` 里这句是无条件追加的：

```js
steps.push('结构升级：若 b 之后又形成第二个不与 A 重叠的中枢 B、再走 c 段，
            就变成 a+A+b+B+c 的趋势结构…');
```

不管当前有几个中枢都会显示。用户读到的就是"我的结构是 a+A+b+B+c"。

现在按实际中枢数分支：
- `n<=1`：明确说"当前是 a+A+b 的盘整结构，**a+A+b+B+c 是趋势骨架，现在还没到那一步**"
- `n>=2`：说明共几个中枢，以及判断趋势要看相邻中枢是否同向不重叠

### ④ 附带的显示歧义

「当前中枢」指的是**最后一个**中枢，不是总数。原先只显示区间和笔数，
用户容易当成"图上一共就这一个"。现在显示 `第 11/11 个（最新）`，
并新增独立一行「中枢总数」。

### 判定口径（写死在代码里）

| 中枢数 | 结构式 | 走势类型 |
|---|---|---|
| 0 | 无线段中枢结构 | — |
| 1 | `a + A + b` | 盘整 |
| 2 | `a + A + b + B + c` | 趋势（A、B 同向不重叠） |
| ≥3 | `a + A + b + B + c + …` | 趋势延伸 |

### 回归测试（4 条）

1. 1 个中枢**绝不允许**出现 `B + c`
2. 中枢数量去掉括号后仍必须存在
3. 前端不得再对 `res.structure` 做 `replace`
4. 教学标注必须有 `nP <= 1` 分支且明确说"还没到那一步"

## 附二：低级错误的系统性排查（v3.11.1）

用户要求"这种低级错误要全面检查一下，然后修复"。所以不只是修个案，
而是把**同类错误变成可机检的规则**。

### 新增审计脚本 `scripts/audit-misleading.js`

起因复盘后发现，"1 个中枢显示 a+A+b+B+c"不是笔误，而是三类可复现的结构性错误。
三类都写成了检测规则，接入 `npm run check:all`：

| 规则 | 检测什么 | 为什么危险 |
|---|---|---|
| ① 删括号 | `replace(/（.*?）/, '')` | 丢掉的不只是排版，可能是"N 个中枢"这类关键限定 |
| ② 固定话术 | 含结构术语、无插值、**且不在 if 分支内** | 无论数据如何都显示，等于骗人 |
| ③ 计数在括号内 | 字符串里把"个中枢"塞进括号 | 前端一旦删括号，语义就丢了 |

### 规则②的精度踩坑（很重要）

第一版用"花括号深度 > 1 就跳过"判断是否在条件分支内 —— **完全失效**：
`highlight.js` 的主逻辑本身就嵌套在 2-3 层函数里，深度永远 > 1，
于是所有固定话术都被放过。

改成：向上找最近的 `if (`，检查该条件的括号在此 push 之前是否已闭合、
且闭合后紧跟一个尚未闭合的 `{`。这样能准确区分"由数据触发的教学解释"和"无条件话术"。

验证方式（必须做）：**故意注入 bug 再跑审计**。
- 注入到 `if` 分支内 → 不报警（正确，那是条件触发）
- 注入到函数顶层 → 精确报警（正确）

不做这一步，审计脚本就是个摆设。

### 顺带修掉的测试自身错误

`flowcheck` 的「手机版·算卦起卦换卦」偶发失败，排查后**产品无 bug**，
是测试正则写错了：

```js
// 旧：^(乾|兑|离|震|巽|坎|艮|坤)…  ← 页面里先出现"离宫/兑宫"，先命中宫位
// 新：抓「第 N 卦」前面的卦名
```

实际页面显示 `山水蒙（第 4 卦）→ 泽水困（第 47 卦）`，卦名和占次都正常。
旧正则抓到的是"离宫""兑宫"，于是判成"卦名没变"。

> 教训：**测试失败先怀疑测试**。花了 10 分钟查后端 nonce 逻辑，
> 后端 8 次起卦给出 8 个不同卦名，一直是好的。

### 关于"中枢 16 个是不是太多"

一并核查了。结论：**算法没 bug**。
- 800 根日线里 16 个中枢，平均跨度 33 根、间隔约 50 根（2 个月）
- 中枢覆盖 65% 的 K 线，日线笔中枢属正常密度
- 图表已按可视范围过滤中枢，不会画出屏外的

之前怀疑"中枢应由线段而非笔构建"，核查后确认：注释写的"至少三段**次级别**走势"，
日线图上的笔就是次级别走势，用笔构建是对的。改用线段会破坏 8 个下游模块
（`enterBi/leaveBi` 全是笔索引），收益不抵风险。

## 附三：周期按钮缺失与「两份列表漂移」（v3.11.2）

### 现象

用户反馈：加密标的的周期按钮里**没有月线**（截图里只有 日线/周线/4时/60分/15分/5分/1分）。

### 根因：同一份信息维护在两处，各漏各的

| 位置 | 问题 |
|---|---|
| `web/js/pages/structure.js` 的 `PERIODS.CR` | 漏了 `month`，也漏了 `30m` |
| `server/lib/sources.js` 的 `MARKETS.CR.periods` | 同样漏了 `month` |

而后端抓取逻辑**本来就支持**加密月线（Binance `1M`，实测 112 根），
只是配置里没声明。所以这是纯配置漂移，不是能力缺失。

### 修复

两个列表都补齐 `month` 与 `30m`，现在六个市场完全一致：

```
A     ✅  day week month 60m 30m 15m 5m 1m
HK    ✅  day week month
US    ✅  day week month
CR    ✅  day week month 4h 60m 30m 15m 5m 1m
CNF   ✅  day week month 60m 30m 15m 5m 1m
USF   ✅  day week month 60m 30m 15m 5m 1m
```

### 做成门禁规则（审计第 4 条）

「两份列表各自维护」是必然漂移的结构，所以直接把一致性检查写进
`scripts/audit-misleading.js`：

- 后端声明了但前端没按钮 → 报警
- 前端有按钮但后端没声明 → 报警

验证方式依旧是**注入 bug**：把 `month` 从 `PERIODS.CR` 删掉，
审计精确报出 `CR 缺少 month`；恢复后通过。

### 实测

```
加密月线：112 根 K 线 → 2 个中枢 → a + A + b + B + c　趋势 · 2 个中枢
```

顺带说明：这个标的恰好是「2 个中枢」的真实案例，
与 v3.11.0 修的「1 个中枢却显示 a+A+b+B+c」形成对照——
现在两者都会显示正确的结构式和中枢个数。

## 附四：配置单一数据源（v3.11.3）

上一条只修了"周期列表"，用户要求"把这类两边各维护一份的配置也全查一遍"。

### 盘点结果

| 配置 | 重复定义处数 | 是否已漂移 |
|---|---|---|
| 市场名称映射 | **5 处** | ✅ 已漂移——`game.js` 只写了 `{A,HK,US,CR}`，缺 `CNF/USF` |
| 周期名称映射 | **3 处** | 措辞不同（"1分" vs "1分钟"） |

**真正的问题**：市场名称映射在 `game.js` 里缺了两个市场。如果闯关题用到期货标的，
界面上会直接显示 `CNF` 而不是「国内期货」。

### 修复：建立 `server/lib/constants.js`

所有名称定义集中到一处，其余模块只引用：

```
server/lib/constants.js          ← 唯一数据源
  ├─ server/lib/game.js          （原缺 CNF/USF）
  ├─ server/lib/history.js
  ├─ server/lib/symbolnames.js
  ├─ server/lib/sources.js       （PERIOD_NAME）
  ├─ server/index.js             （describeCfg）
  └─ /api/constants              → web/js/ui.js 启动时同步
```

前端 `ui.js` 保留一份**本地兜底值**（API 不可用时仍能显示），但启动后会被
`/api/constants` 覆盖——这是**有意设计的兜底**，不算漂移，已加白名单。

### 前端短名派生

按钮空间有限，显示名要比后端短：

```
后端 "1分钟"  → 按钮 "1分"     replace(/钟$/, '')
后端 "4小时"  → 按钮 "4时"     replace(/小时$/, '时')
后端 "日线"   → 按钮 "日线"    （不变）
```

`structure.js` 和 `mobile.js` 都从 `U.PERIOD_NAMES` 派生，不再各自维护一份。

### 顺带修掉：手机版也缺月线

盘点时发现手机版的 `PERIODS.CR` **同样缺 `month`**——
v3.11.2 只修了桌面版，这是当时漏改的。现在两边都补齐。

### 审计第 5 条

`audit-misleading.js` 新增「配置漂移」规则：

- 除 `constants.js` 外，任何文件不得重新定义市场/周期名称字面量

现在审计共 **5 条规则**，全部接入 `check:all`。

## 附五：借鉴 Duodecimal 的信息组织（v3.12）

用户给了两个参考站：`duodecimal.capital` 主页与 `/learn/wiki`。

### 一、先把对方是怎么做的拆清楚（实测，不是猜）

**主页动效**

| 层 | 实现 | 实测数据 |
|---|---|---|
| 底 | `background: rgb(10,10,10)` | 纯黑 |
| 动效 | `position:fixed` 的全屏 `<canvas id="home-underlay">` | 1440×900 |
| 亮度 | —— | **90% 暗区 + 0.25% 亮点**，最亮 `RGB(90,147,179)` |
| 滚动 | 形态随 scrollY 改变 | 顶部=散景光点 → 中段=**旋转粒子环流** |

配色：`rgb(6,147,227)` 蓝、`rgb(34,211,238)` 青、`rgb(34,197,94)` 绿、`rgb(249,115,22)` 橙。

**Wiki 页**

- 布局：左侧 **224px sticky 目录** + 右侧正文（`main` 宽 1280）
- 规模：13 个分类、**17 个表格**、33330 字
- 每个指标统一四段：**一句话定义 → 拆解表（信号/含义）→ 算法口径 → 出现在哪**

### 二、我们怎么用（刻意不做全站照搬）

我们是**工具站**，不是门户站。背景一动，看 K 线就分心。所以：

| 项 | Duodecimal | 我们 | 理由 |
|---|---|---|---|
| 动态背景 | 全站 | **只在总览页** | 结构/回测/量化页要专注看图 |
| 亮度 | 0.25% 亮点 | **0.09%** | 更克制，不对内容造成干扰 |
| 减少动效 | 未处理 | **尊重 `prefers-reduced-motion`** | 系统开了就只画静态帧 |
| 首屏 | 大标题+星系图 | **保持工具风格** | 用户明确选择 |
| Wiki | 指标辞典 | **概念辞典（四段式）** | 内容适配缠论深度 |

### 三、概念辞典：四段式映射

我们的字段刚好覆盖 Duodecimal 的四段：

| Duodecimal 段 | 我们的字段 | 渲染 |
|---|---|---|
| 是什么 | `definition` + `original` | 定义直接显示，**原文要义折叠** |
| —— | `howTo` | 怎么判定（有序步骤） |
| —— | `mistakes` | 怎么读（常见误读，无序列表） |
| 出现在哪 | `station` | **图上在哪** |

实测：40 个概念全部四段齐全（`what/how/read/where` 各 40）。

### 四、过程中修掉的两个真 bug

**① `#theoryBody` 在 HTML 里根本不存在**

`theory.js` 一直引用 `U.$('#theoryBody')`，但 `index.html` 里没有这个元素。
我插入 wiki 容器时才注意到——这意味着**非概念 tab（问答/108课/言论集/择时/命理）此前全部渲染失败**。

**② 雷达接口首包 17.4 秒，超时门槛 20 秒**

实测 `/api/radar?scope=all` 首次 **17365ms**、之后 16ms（有缓存）。
离 20 秒超时只差 2.6 秒，网络一抖就 `ERR_ABORTED`，
页面显示「雷达暂不可用: signal is aborted without reason」。

修复：API 客户端加 `SLOW_PATHS`，按路径给不同超时：
```
/api/radar          60s
/api/overview       40s
/api/bt/* /api/quant/*  180s
```

### 五、flowcheck 的固定等待改成轮询

数据源页要探测 10 个外部接口，原来固定等 3.5 秒，CI 环境偶尔不够。
改成**最多轮询 12 次、每次 1 秒**，出结果就停。
```
✗ 桌面版·数据源页有探测结果 — 命中 0
✓ 桌面版·数据源页有探测结果
```

### 六、教训：改 UI 结构会打断既有测试

我把概念卡片（`.concept`）改成 wiki 条目（`.wiki-item`），
flowcheck 的「理论概念弹窗」立刻失败（它找 `.concept`）。

修法不是改测试，而是**给 wiki 条目补上 `data-concept` 属性并绑定点击**——
既保留新布局，又不丢原有能力（弹窗里还有「在结构图上标注并分步导读」）。

> 改结构时先想：这个元素是不是被测试或别处代码依赖着？
